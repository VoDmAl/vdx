# Спека: формат `vdx-environment.yaml`

Статус: **draft v0.1**. Личная половина набора (сета) рубрики: как человек
запускает агента в проекте. Проектная половина — `vdx-rubric.yaml`
([rubric-format.md](rubric-format.md)). См. [../decisions.md](../decisions.md) D14.

Читают `vdx ai` и `vdx doctor`: doctor — личные хуки (`git.hooks`, vdx 0.22+),
первую проверку окружения из этого документа (O40).

## Где лежит и как vdx его находит

Документ живёт в персональном сете рядом с рубрикой — у владельца это
`vdx-rubric-vodmal/vdx-environment.yaml`, под тем же semver-тегом. В CLI он
**не вшивается**: какой агент и с какими правами — выбор человека, и опасный
флаг не должен доставаться тому, кто его не выбирал.

Порядок поиска:

1. `$VDX_ENVIRONMENT` — путь к файлу (`~` раскрывается). Если переменная
   задана, а файла нет, — ошибка, а не тихий откат.
2. `~/.vdx-environment.yaml` — обычно симлинк на файл в клоне сета.
3. Ничего не найдено → встроенный дефолт: `claude`, если он на `PATH`, иначе
   `codex`; без флагов, без tmux.

## Схема

```yaml
schema_version: "0.1"

metadata:                    # свободная форма, vdx не читает
  name: vdx-environment-vodmal
  version: "0.4.0"
  owner: vodmal

agent:
  command: claude            # обязательно, если секция есть
  args: [--dangerously-skip-permissions]
  resume_args: [--continue]  # продолжать разговор; у claude vdx выбирает его сам
  when:                      # условные флаги проекта
    - id: echelon-channel    # обязательно, уникально по смыслу
      description: "…"
      if:                    # обязательно — предикат рубрики
        has_file: {path: signals/sources.yaml}
      args: [--dangerously-load-development-channels, plugin:echelon@echelon]
      wakes: true            # правило будит агента: --focused его пропускает
      confirm:               # окна, которые этот флаг вызывает
        - screen: "Loading development channels"
          keys: [Enter]      # имена клавиш tmux: Enter, Down, Escape, …

session:
  multiplexer: tmux          # tmux | none; по умолчанию none
  name: "{project}@{host}"   # по умолчанию "{project}"
  machines: [lft, m3]        # где может идти агент проекта; по умолчанию —
                             # только машины, названные в разговорах
  folders_fix: "…"           # что делать, если сессия не читает ~/Downloads …
```

## Поля

### `agent`

- `command` — исполняемый файл агента. В tmux он запускается через
  login-shell пользователя, поэтому годится и alias из `.zshrc`; без tmux —
  напрямую, и тогда команда должна быть на `PATH`.
- `args` — флаги при каждом запуске.
- `resume_args` — флаги продолжения разговора. Добавляются к каждому запуску и
  перезапуску: после перезагрузки `vdx ai` возвращает агента к последнему
  разговору в проекте, `--restart` не теряет контекст. `--new` их убирает.
  Если агент с ними сразу завершился — продолжать нечего, — vdx один раз
  запускает его без них: в tmux это видно по процессу, без tmux — по ненулевому
  коду выхода в первые 30 секунд. Для `claude` непустой `resume_args` значит
  «продолжать», а какой разговор — vdx выбирает сам и передаёт `--resume <id>`
  (см. «Какой разговор продолжается»).
- `when[]` — условные флаги. `if` — любой предикат рубрики (`has_file`,
  `file_contains`, `config_value`, `all_of`/`any_of`/`not`, …; см.
  [rubric-format.md](rubric-format.md)), вычисляется по файлам проекта. При
  истинном условии к запуску добавляются `args`, а `confirm` становится
  ожидаемым окном. `wakes: true` — правило нужно, чтобы агента будили (флаг
  канала): сессия `vdx ai --focused` его пропускает — ни `args`, ни `confirm`
  (см. «`vdx ai --focused`»).

### `confirm[]`

Окно, которое агент **гарантированно** покажет из-за условного флага, и
клавиши, которые на него отвечают. Работает только в tmux: vdx читает экран
(`tmux capture-pane -J`), находит `screen`, шлёт `keys` по одной и ждёт, пока
текст уйдёт с экрана. Если ожидаемое окно не появилось за 30 секунд — на экране,
скорее всего, другой вопрос; vdx показывает последние строки панели и
подключает человека (в терминале) или выходит с кодом 4.

Правила для окон, которые могут и не появиться, нет намеренно. Пример —
вопрос Claude Code о доверии к новой папке: курсор в нём стоит на «No, exit», а
ответ «да» снимает защиту от чужого репозитория. На такой вопрос отвечает
человек.

### `session`

- `multiplexer: tmux` — агент стартует в tmux. Если tmux не установлен, vdx
  сообщает об этом и запускает агента в текущем терминале.
- `name` — имя **новой** сессии. Плейсхолдеры: `{project}` — короткое имя
  проекта (ниже); `{host}` — `$VDX_HOST`, иначе короткое имя хоста. Точки и
  двоеточия заменяются на `_`, как это делает tmux. Неизвестный плейсхолдер —
  ошибка.
- `project_names` — откуда ещё брать `{project}`. Порядок: `[vdx] name` в
  `mise.toml` проекта ([manifest-format.md](manifest-format.md)), затем
  источники из этого списка по очереди, затем имя репозитория из `origin` (в
  нижнем регистре), иначе имя каталога. Источник — структурный файл
  (`.json`/`.yaml`/`.toml`) и путь через точку внутри него (`names.0` — первый
  элемент списка). В `file` плейсхолдер `{repo}` — имя репозитория, `~` —
  домашний каталог; относительный путь — от каталога профиля. Нет файла, нет
  значения или оно не строка — источник пропускается: имя — подпись, не повод
  отказать в запуске. `--dry-run` показывает имя и откуда оно взято.

  ```yaml
  session:
    name: "{project}@{host}"
    project_names:
      - file: "~/.claude/vdm/intercom/_registry/{repo}.json"   # каталог intercom (vdm)
        jsonpath: names.0
  ```

  Бегущую сессию со старым именем vdx не переименовывает: новое имя получит
  сессия, созданная после смены.
- `machines` — машины, на которых может идти агент проекта: адреса для ssh,
  они же метки (`$VDX_HOST`). Перед запуском vdx спрашивает остальные, какие
  сессии Claude Code там идут и в каких каталогах (см. «Какой разговор
  продолжается»); свою машину — по метке — не спрашивает. Без списка
  спрашиваются только машины, названные в разговорах проекта. Имя, похожее
  на опцию ssh (`-o…`), — ошибка профиля. Каждая молчащая машина — до 5 с
  ожидания при каждом запуске.

  ```yaml
  session:
    machines: [lft, m3]
  ```

- `folders_fix` — строка «fix:» под предупреждением о папках, которые сессия
  не читает (ниже, «Папки `~/Downloads`, `~/Desktop`, `~/Documents`»): как это
  лечится на машинах владельца. Без ключа vdx пишет общее — перезапустить
  сервер tmux (закроет все сессии) или, без tmux, дать терминалу доступ в
  System Settings.

### `git`

- `author_pool` — каталоги, в которых лежат репозитории (на один уровень
  вглубь). Их авторы — адреса, из которых vdx предлагает автора коммитов
  репозиторию, где своего нет (ниже). `~` — домашний каталог, относительный
  путь — от каталога профиля. Без списка — репозитории рядом с проектом.

  ```yaml
  git:
    author_pool: ["~/AI Projects", "~/PhpstormProjects"]
  ```

- `hooks` (vdx 0.22+) — личные хуки: гейты владельца, которые действуют в
  каждом репозитории машины. Живут в конфиге git пользователя (`hook.<имя>.*`
  в `~/.gitconfig`, Git 2.54), а не в каждом репо, где воевали бы с фреймворком
  хуков самого репо за одно место. Поля:

  - `name` — имя хука, подраздел конфига git: буквы, цифры, `. _ -`;
    уникально;
  - `event` — событие git (`pre-commit`, `pre-push`, …) или список;
  - `command` — команда; git запускает её через shell, `$HOME` и кавычки
    работают как в скрипте хука;
  - `when_exists` — хук действует на машине, где есть этот путь (инструмент
    установлен); `~` — домашний каталог. Без поля — на любой;
  - `description` — свободный текст.

  ```yaml
  git:
    hooks:
      - name: vdm-crystal
        event: pre-commit
        command: '"$HOME/.claude/plugins/marketplaces/vodmal/plugins/vdm-git/scripts/crystal-precommit-check.sh"'
        when_exists: "~/.claude/plugins/marketplaces/vodmal/plugins/vdm-git/scripts/crystal-precommit-check.sh"
  ```

  `vdx doctor` проверяет строкой `personal hooks`: хук есть в `~/.gitconfig`
  с той же командой и событием; git на этой машине не старше 2.54 — старый
  git такие ключи пропускает молча, и doctor говорит об этом вслух; программа,
  которую зовёт команда, есть на машине. Репозиторий, где хук не нужен,
  выключает его у себя: `git config hook.<имя>.enabled false` (или своей
  командой, `hook.<имя>.command`), — doctor называет это, но не считает
  ошибкой. `vdx doctor --fix` пишет недостающие и разошедшиеся хуки в
  `~/.gitconfig`; больше ничего не трогает.

## Поведение `vdx ai [path]`

Проект — git toplevel для `path` (по умолчанию cwd), иначе сам каталог.

| Состояние (tmux) | Без флагов | `--restart` |
|---|---|---|
| Агента проекта нет | новая сессия `name` (или новое окно, если сессия с таким именем есть), продолжая разговор | то же |
| Агент есть, флаги как в профиле | подключиться | перезапуск в той же панели, продолжая его разговор |
| Агент есть, флагов не хватает | в терминале — вопрос: Enter — подключиться как есть, `r` — перезапуск с профилем, `q` — ничего (с 0.24); без терминала — отчёт о дрейфе, код 3, ничего не трогать | перезапуск в той же панели, продолжая его разговор |

`--new` запускает агента без `resume_args` — с новым разговором; бегущего агента
заменяет только вместе с `--restart`. `--conversation <id>` — продолжить этот
разговор Claude Code, без вопросов; бегущего агента тоже трогает только с
`--restart` (и говорит, если тот в другом разговоре). `--resume` (в 0.12 —
просьба продолжить разговор) принимается и ничего не меняет.

### Папки `~/Downloads`, `~/Desktop`, `~/Documents` (macOS)

У этих трёх папок своя защита macOS, и живой сервер tmux может держать отказ
для всех своих сессий (разбор — nas-info, `docs/features/shared-terminal.md`,
«Доступ к файлам в сессиях tmux»; письмо `vdx-ai-folders-warning`, DL #33
кристалла vdx-ai). Перед запуском и перед подключением vdx проверяет, читает
ли их сессия, и если нет — пишет одну строку и `fix:` (`session.folders_fix`,
иначе общее), агента не задерживая:

```
⚠ this session cannot read ~/Downloads — macOS holds the denial in the tmux server; files there are out of the agent's reach
  fix: ~/nas-info/gather-and-send-info.sh in a plain terminal, not under tmux
```

- В tmux проверяет сам сервер (`tmux run-shell`, `ls` каждой папки): у сессий
  права сервера, а не процесса `vdx` в терминале. Сервера ещё нет — проверяет
  vdx: сервер он поднимет из этого терминала. Без tmux — тоже vdx: агент
  получит права терминала.
- `ls`, а не `[ -d ]`: отказ проходит `-d`. Папку, которой нет, пропускает.
- Только macOS; в `--dry-run` — те же строки.

### `vdx ai --focused`

Сессия, которую никто не будит: агент работает над тем, что дал человек, и
сам не читает входящие (слова владельца 08.10 — письмо echelon
`vdx-focused-flag`, DL #32 кристалла vdx-ai).

- Агент получает `VDX_FOCUSED=1` в окружении; его наследуют хуки и
  MCP-серверы сессии. По ней молчат части, которые будят и напоминают
  (echelon, intercom), и сессию не выбирают для побудки — это их сторона.
- Правила `when[]` с `wakes: true` пропускаются: без флага канала Claude Code
  сам отбрасывает события echelon. В `--dry-run` — строка `focused:` и какие
  правила пропущены.
- Режим идущего агента vdx читает из его окружения (`ps -E` на macOS,
  `/proc/<pid>/environ` в Linux; у собственных бинарников Apple окружение
  скрыто, у `claude` — видно). Агент сохраняет свой режим:
  - `vdx ai` без флага подключается к focused-агенту как есть — пропущенный
    флаг канала не дрейф;
  - `vdx ai --focused` к обычному агенту — тот же вопрос, что при дрейфе
    (`r` перезапускает его focused); без терминала — отчёт, код 3 и команда
    `vdx ai --restart --focused`;
  - `--restart` ставит режим этого вызова: без `--focused` агент станет обычным.
- `VDX_FOCUSED` из окружения самого `vdx` агенту не передаётся: режим задаёт
  флаг, а не оболочка, в которой vdx запущен.
- `vdx ai@<host> --focused` передаёт флаг; vdx старше 0.23 его не знает и
  откажет.

### Какой разговор продолжается (Claude Code)

Для агента `claude` vdx выбирает разговор сам; у других агентов — `resume_args`
как есть. `--continue` берёт самый свежий разговор в каталоге проекта
(`~/.claude/projects/<путь>/`, `$CLAUDE_CONFIG_DIR`), а если этот каталог
синхронизируется между машинами — разговор, который другая машина ещё пишет.
Так 2026-10-04 `vdx ai` на m3 продолжил беседу, живую на lft, и Syncthing
оставил конфликтную копию транскрипта (Sidetrack #15 кристалла vdx-ai).

Чей разговор:

- Первая строка `vdx ai --check` — ``vdx ai: this machine is `<метка>`; …``.
  Хук плагина отдаёт её агенту, и Claude Code сохраняет её в транскрипте при
  каждом старте, `--resume`, `/clear` и compact. Последняя такая строка —
  машина разговора. Метка — `$VDX_HOST`, иначе короткое имя хоста; она же адрес
  для `vdx ai@<метка>`, поэтому метка из транскрипта, похожая на опцию ssh,
  отбрасывается.
- Разговор без такой строки (до 0.19 или без плагина) — этой машины, если в нём
  печатали здесь: `~/.claude/history.jsonl` хранит разговор каждого набранного
  промпта и у владельца не синхронизируется. Иначе машина неизвестна.
- Что идёт прямо сейчас: на этой машине — файлы сессий
  `~/.claude/sessions/<pid>.json` живых процессов (разговор в них следует за
  `/clear`); у других машин — `session.machines` профиля и названных в
  разговорах проекта — те же файлы по ssh (`BatchMode`, 5 с), с домашним
  каталогом той машины. Идущий разговор называет и свою машину. Каталог
  сессии (`cwd`) говорит, что там идёт агент этого проекта: пути сравниваются
  от домашних каталогов (`~/AI Projects/x` на обеих машинах).

Что запускается:

| Разговоры проекта | С терминалом | Без терминала и в `--dry-run` |
|---|---|---|
| нет ни одного | новый разговор (\*) | новый разговор (\*) |
| все — этой машины и ни один не идёт здесь | самый свежий, без вопроса | то же |
| иначе | список: самый свежий у каждой машины и все идущие, с пометками; Enter — самый свежий, цифра — другой, `n` — новый | самый свежий незанятый этой машины, иначе новый (\*); остальные — строками `note` с командой для них |

(\*) Новый разговор, которого человек не выбирал в списке, — и `--new` — при
агенте этого проекта на другой машине запускается только после «да»: vdx
называет агента и команду для него (``an agent of this project is running on
m3 now (…) — there: vdx ai@m3 <путь>``) и спрашивает «Start a new conversation
here, on lft, anyway? [y/N]». Команда — только для агента в tmux: к агенту в
своём терминале (в строке `pid`, а не имя сессии) `vdx ai` не подключается.
Без «да» и без терминала ничего не запускается (код 4).
Агент на другой машине — не запрет: работать в одном репо с двух машин
можно (DL #17 кристалла vdx-ai), но вслепую второй не поднимается.
`--restart --new` заменяет агента здесь и ничего не спрашивает.

Разговор другой машины продолжается на ней: `vdx ai@<машина> <путь>
--conversation <id>` — её vdx подключается к агенту, если тот там идёт, иначе
запускает его с этим разговором. Если машина не ответила по ssh, если она
неизвестна или если разговор уже идёт здесь вне tmux, vdx спрашивает
«продолжить здесь? [y/N]»; без «да» ничего не запускается (код 4). Без
терминала такой разговор не берётся никогда.

Машина, не ответившая по ssh, названа строкой ``note: <машина> does not answer
over ssh — what runs there is not known`` — под списком, до выбора, и при
выборе без вопроса: её разговор может идти, хотя пометки «running» нет.
Частый случай — вход на эту машину по ssh без агента ключей: ключ, которым
пускает соседняя, лежит в агенте, а BatchMode пароль не спросит.

`--restart` продолжает разговор, в котором агент сейчас (по его файлу сессии).

Переходный период: машина, где ещё не стартовала сессия с vdx ≥ 0.19 и
плагином, в разговорах не названа. Без `session.machines` vdx не знает, что её
надо спросить, и её разговор, в котором здесь не печатали, виден как «машина
неизвестна»; со списком (vdx ≥ 0.21) идущий там разговор узнаётся по файлу
сессии. Разговор, который там уже не идёт, остаётся «машина неизвестна».

Агенты, кроме `claude`, не видны на других машинах: vdx читает только файлы
сессий Claude Code.

«Агент проекта» ищется по процессу, а не по имени сессии: панель tmux, чей
рабочий каталог лежит в проекте и под которой запущен `command` (напрямую или
скриптом под `node`/`sh`/…). Флаги сверяются по командной строке процесса из
`ps`.

После запуска vdx отвечает на ожидаемые окна и проверяет, что агент жив (виден
дважды с интервалом в секунду) и несёт все флаги профиля. Затем подключает
терминал (`attach`, внутри tmux — `switch-client`); без терминала или с
`--detach` печатает команду подключения.

### Автор коммитов

Если git не знает, кто коммитит в проекте (`user.email` нет ни в
`.git/config`, ни глобально — при `user.useConfigOnly` git откажет), `vdx ai`
перед запуском предлагает автора. Кандидаты — только адреса, которые уже стоят
автором у какого-то репозитория из `git.author_pool`; голосуют история проекта
(коммиты этими адресами), репозитории той же группы в remote (`host/group`) и
репозитории со схожим именем; до трёх вариантов, остальные адреса — по числу
репозиториев. Enter записывает первый в `.git/config` (`user.name` и
`user.email`), цифра — другой, адрес — как введён, `s` — пропустить. Без
терминала vdx только печатает команду и запускает агента дальше. Бегущему
агенту перезапуск не нужен: git читает автора при каждом коммите. `vdx doctor`
в проекте показывает автора или вероятного кандидата с командой.

по остальным: первым правильный адрес — в 31, среди первых трёх — в 37.

### `vdx ai@<host>`

Та же команда на другой машине: `ssh <host> vdx ai <путь> <флаги>`. Там свой
vdx, свой профиль и свой tmux; сессия получает метку той машины (`vdx@m3`).

- Путь внутри домашнего каталога переносится под домашний каталог той машины,
  вне его — как есть. Если путь есть здесь, проект определяется здесь (git
  toplevel).
- Путь идёт первым, флаги после: vdx 0.12 отдаёт токен после незнакомого флага
  этому флагу.
- ssh получает терминал (`-t`), когда будет подключение; с `--detach` и
  `--dry-run` — нет (`-T`). После `--detach` vdx печатает `vdx ai@<host>
  <путь>` — подключиться отсюда. Внутри tmux удалённая сессия открывается
  вложенной.
- Другая версия vdx на той машине — предупреждение, запуск идёт.
- `<host>` — имя для ssh (`m3`), не опция ssh. Метка этой машины (`$VDX_HOST`)
  — обычный запуск здесь.
- Метку своей машины vdx передаёт туда (`VDX_AI_FROM`, с 0.22.1), и vdx там
  говорит с места человека: его машина — «where you are», команда к ней — без
  `@` (`attach: vdx ai <путь>`; ssh на саму себя не работает), а та машина —
  по имени, не «here» (`Start a new conversation on m3 anyway?`). Агенту,
  которого vdx там запускает, переменная не достаётся. vdx старше 0.22.1 её
  пропускает и говорит от лица своей машины.

Без `@host` vdx подключается только к агенту на этой машине. Другие машины
(`session.machines` и названные в разговорах) он спрашивает перед запуском
(см. «Какой разговор продолжается»): их идущий разговор виден в списке и
выбор ведёт туда, а новый разговор при агенте проекта там — только после
«да».

`--dry-run` печатает план и состояние бегущих агентов проекта, ничего не
запуская.

### `vdx ai --check`

Для сессии самого агента: как в проекте запускается агент и несёт ли эта
сессия флаги профиля. Агент ищется среди предков процесса `vdx` — ближайший,
в ком узнаётся `command` (как при поиске в панели, DL #5 кристалла); флаги
сверяются с планом проекта, как у бегущего агента в tmux.

- Профиля нет — ничего не печатает, код 0: на такой машине `vdx ai` ничего не
  решает.
- Первая строка всегда: метка этой машины (``vdx ai: this machine is `lft`;`` —
  по ней vdx потом узнаёт машину разговора), агент здесь запускается `vdx ai`,
  флаги — в профиле (путь), `agent.args` и `agent.when[]`; человеку давать
  `vdx ai`, а не `<agent> --<flag>`; агент проекта на другой машине —
  `vdx ai@<машина>`.
- Сессия focused (`VDX_FOCUSED=1` в окружении хука) — строка об этом: её
  никто не будит, входящие она читает, только когда попросит человек; правила
  `wakes` пропущены и не считаются недостающими.
- Флаги на месте — `✓` и сработавшие условия, код 0. Не хватает — `✗`, каких
  флагов и каких условий ради, и что дать человеку, код 3: в tmux — `vdx ai
  --restart <корень>` с пометкой, что из самой сессии его не запускать (он её
  остановит); вне tmux — выйти и запустить `vdx ai <корень>`.
- Агента среди предков нет (запуск руками из терминала) — так и пишет, код 0.
- Только путь: `--check` с другими флагами или `@host` — ошибка вызова.

Плагин vdx зовёт его в SessionStart-хуке и отдаёт ответ агенту через
`additionalContext` — только если `vdx --version` не ниже 0.18: до 0.16
`vdx ai` принимал незнакомый флаг за запуск.

`--help` и `-h` печатают справку: флаги, где живут флаги запуска, коды выхода.
Незнакомый флаг или второй путь — ошибка вызова: код 2, ничего не запускается.
В 0.15.0 и раньше и то и другое молча отбрасывалось, и `vdx ai --help` запускал агента в
текущем каталоге.

Коды выхода: `0` — агент работает по профилю; `2` — ошибка профиля или вызова;
`3` — дрейф без `--restart`, оставленный как есть: без терминала или `q` на
вопрос (и обычный агент при `--focused`); `4` — запуск не
подтвердился.
